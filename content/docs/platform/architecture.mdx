# Application Architecture

TolaMandi follows a modern full-stack architecture built on **Next.js App Router** with **Supabase** as the backend-as-a-service layer.

## Route Groups

The application uses Next.js **route groups** to separate concerns by role:

<Tabs items={['(auth)', '(dashboard)', '(superadmin)', '(mobile)']}>
  <Tab value="(auth)">
    **Authentication Routes** — `/login`

    Single login page shared by all roles. After authentication, users are redirected based on their role:
    - Super Admin → `/superadmin/dashboard`
    - Owner / Buyer Admin → `/dashboard`
    - Operator → `/mobile/dashboard`
  </Tab>
  <Tab value="(dashboard)">
    **Owner & Admin Dashboard** — `/dashboard/*`

    Full desktop interface for organization owners and buyer admins. Includes:
    - Dashboard with daily stats
    - Transactions table with filters and export
    - Masters (commission agents) management
    - Operators management
    - Organization settings
    - Billing and subscription info
    - User settings
  </Tab>
  <Tab value="(superadmin)">
    **Platform Administration** — `/superadmin/*`

    Dedicated interface for the platform super admin. Manages:
    - All organizations and owners
    - Subscription plans
    - Produce catalog
    - APMC groups
    - Platform settings
    - Audit logs
  </Tab>
  <Tab value="(mobile)">
    **Mobile Operator Interface** — `/mobile/*`

    Mobile-first interface for field operators. Features:
    - Today's transaction dashboard
    - 5-step weighing wizard
    - Past entries with search
    - Operator profile
  </Tab>
</Tabs>

## Data Flow Pattern

<Steps>
  <Step>
    ### Database Layer (Supabase PostgreSQL)
    All data stored in PostgreSQL with snake_case column naming. Row-Level Security (RLS) policies enforce multi-tenant isolation. Every query filters by `organization_id`.
  </Step>
  <Step>
    ### Service Layer (`lib/supabase/services.ts`)
    Business logic functions that query Supabase, handle validation, and return typed results. Contains 50+ exported functions covering all CRUD operations.
  </Step>
  <Step>
    ### Data Mapping Layer
    Mapper functions (`mapDbTransactionToApp()`, `mapDbAgentToApp()`, etc.) convert database snake_case responses to application camelCase TypeScript interfaces.
  </Step>
  <Step>
    ### Hooks Layer (`lib/supabase/hooks.ts`)
    React hooks that wrap service calls with state management, loading indicators, and real-time subscriptions. Example: `useTodayProduceSummary()`, `useRealtimeTransactions()`.
  </Step>
  <Step>
    ### Component Layer
    Feature-organized React components that consume hooks and render the UI. Components are organized by domain: `components/transactions/`, `components/commission-agents/`, `components/operators/`.
  </Step>
</Steps>

## Context Providers

| Provider | File | Purpose |
| --- | --- | --- |
| `AuthProvider` | `contexts/auth-context.tsx` | User state, roles, org switching, impersonation |
| `PlatformProvider` | `contexts/platform-context.tsx` | Dynamic platform name and tagline |
| `I18nProvider` | `components/i18n-provider.tsx` | i18next with 9 namespaces (en + gu) |
| `RootProvider` | Next.js root layout | Wraps all the above providers |

<Callout title="Multi-Tenant Isolation" type="warn">
  Every database query is scoped to the user's `organization_id`. Supabase RLS policies enforce this at the database level, providing defense-in-depth even if application logic has bugs.
</Callout>
